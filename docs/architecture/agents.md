# Agents

Status: plan. Nothing here is built yet.

How agents find the schemas that apply to their work, and validate their output against them. The binding contracts (MCP tool names and parameters, CLI options and output, exit codes) will be added here once they are built.

## Agent types

| Agent | Sees | Validates through |
|---|---|---|
| **Coding agent with a shell** (Claude Code, Codex, Aider) | Files, command output | The CLI |
| **Agent with MCP** (Claude Code, Claude Desktop, Cursor; hosted agents via remote MCP) | The MCP server's tools | The MCP server |
| **Function-calling agent** (tool use, structured outputs via an API) | Only the JSON Schema in its tool definitions | The application around it: constrained decoding by the provider, then full validation in the tool implementation |

## Discovery

- **`$schema` in every schema file,** published at stable URIs, so agents and editors can follow it.
- **An `AGENTS.md` / `CLAUDE.md` snippet,** generated by an integration for a project. It says which files are validated, how to run the validator, and where the site schema dump is.
- **`llms.txt`** ([llmstxt.org](https://llmstxt.org)): a compact overview of the spec and keywords.
- **Slices instead of whole dumps:** agents ask for the schema they need, and look up catalogs on demand. Catalogs can be large.

## CLI

```
portable-schema validate <file> --schema <id> --dump <path> --format json
```

- **Output:** the result format of [`spec/errors.md`](../../spec/errors.md), plus the English messages.
- **Exit codes:** deterministic, so agents and CI can rely on them.
- **The same tool runs linting** ([roadmap](../roadmap.md)).

## MCP server

| Tool | Purpose |
|---|---|
| `describe_schema(id)` | The schema, with references resolved as far as needed |
| `list_types()` | Types and catalogs available |
| `get_catalog(id, filter)` | Catalog entries, filtered, so large catalogs don't flood the context |
| `validate(schema_id, data)` | The result, plus messages |

| Mode | Started by | Source |
|---|---|---|
| **Local (stdio)** | The host, e.g. `npx -y portable-schema mcp --dump ./site-dump.json` or the PHP equivalent | A site schema dump |
| **Remote (HTTP)** | Deployed; e.g. live through the Drupal integration (mcp_server / Tool API) | The running site, or a dump |

Hosted agents without local processes (browser, API-side) need the remote mode.

```json
{
  "mcpServers": {
    "portable-schema": {
      "command": "npx",
      "args": ["-y", "portable-schema", "mcp", "--dump", "./var/portable-schema/site-dump.json"]
    }
  }
}
```

## Claude Code

- **A skill:** how to find the relevant schema, validate, read errors and fix them. Loaded only when needed.
- **A hook:** `PostToolUse` on `Edit` / `Write` for validated files (e.g. `config/**/*.yml`) runs the CLI and feeds errors back, so the agent corrects itself.
- **Optionally a plugin** bundling skill, hook and MCP server.

## Function-calling agents

The model only sees the tool definitions. Portable Schema helps in three ways:

1. **LLM export.**
   - The tool's parameter schema is exported to the subset the provider supports, e.g. OpenAI's strict mode needs `additionalProperties: false` and all properties in `required`.
   - Where providers do constrained decoding, the model can only produce what that subset allows.
   - **Lost in the export:** `portable-typeBy`, `-check`, `-compare`, `-refine`, and catalogs too large to inline.
2. **Repair loop.**
   - The tool implementation validates the arguments against the full Portable Schema.
   - Errors go back as the tool result, with messages and suggestions, e.g. `plugin: "system_brandng_block" is not an allowed value. Did you mean "system_branding_block"?`.
   - The model corrects itself and calls again.
3. **Progressive disclosure.**
   - What doesn't fit a static tool schema is split into steps, each with an exact schema.
   - Example: `create_block(plugin, region, …)` with the plugin catalog as `enum`, plus `get_block_settings_schema(plugin)` returning the settings schema for the chosen plugin.
   - This replaces `portable-typeBy` with a choice the model makes in two steps.

## Errors for agents

- **Location, code, params and message,** as for humans.
- **"Did you mean" suggestions** for catalog and `enum` errors.
- **Unchecked checks stay explicit,** so an agent doesn't assume a check passed when it never ran.
