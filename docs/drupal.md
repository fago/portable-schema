# Portable Schema and Drupal

How Portable Schema relates to what Drupal uses today to describe and validate data. Drupal's needs drive the design, but Portable Schema has no Drupal dependency; a Drupal integration generates the Drupal-specific types and catalogs.

## Why Drupal benefits

When Drupal describes and validates its data with Portable Schema:

- **Agents become config-schema-aware.** They know exactly which data a config object needs, including plugin-specific settings, and write and validate Drupal config locally, statically against a site schema dump.
- **Tools, entities and config share one schema.** Tool API inputs and outputs reference the same types as entity fields and config, so data passes from a tool to an entity or config object without mapping, and is validated the same way.
- **UIs can be generated from schemas,** for example config forms and component props (SDC, Canvas), with widgets, validation and messages.
- **Modern UIs get easy.** Drupal forms and client-side forms are based on the same schema, so UIs like Canvas use the same structure, widgets and validation on the server and in the browser.
- **Entity APIs with full schemas.** JSON:API or a similar API serves complete schemas for entities and their fields, so clients generate UIs from them and agents understand and validate the data.
- **One validation everywhere.** The server, the browser and agents run the same rules with the same errors.

Limits: static validation holds for an unchanged code base and module set. Checks that need site data, such as references or uniqueness, run on the server or remotely through the site's API. Details for agents: [`architecture/agents.md`](architecture/agents.md).

## Overview

| Drupal | What it describes | Portable Schema equivalent |
|---|---|---|
| **Config schema** (`config/schema/*.schema.yml`) | Simple config and config entities | Schemas generated by the integration, using the type library |
| **Typed Data** (DataType plugins, data definitions) | Primitive and complex data, entity fields, plugin contexts | The type library; schemas generated from data definitions |
| **Validation constraints** (Symfony constraint plugins) | Rules on any typed data | Standard keywords, catalogs and `portable-check` |
| **SDC / Canvas props** (JSON Schema draft-04 / 07) | Component props | Portable Schemas are valid JSON Schema; down-level export for older drafts |

Config schema is built on Typed Data: each config schema type is a typed data definition, validated by the same constraint plugins.

## Config schema

### Structure

| Config schema | Portable Schema |
|---|---|
| `type: mapping` with `mapping:` keys | `type: object` with `properties` |
| `type: sequence` (list) | `type: array` with `items` |
| `type: sequence` (keyed) | `type: object` with `additionalProperties` |
| Type inheritance (`type: config_entity` plus extra keys) | `$ref` to the base type, plus the extra `properties` |
| Mappings closed by default (`ValidKeys: <infer>`) | Concrete types close with `unevaluatedProperties: false`; base types stay open |
| All keys required by default; `requiredKey: false` | `required` lists the required keys, for `FullyValidatable` types only ([below](#required-keys-and-null)) |
| `nullable: true` | `type: [<type>, "null"]`; an `enum` also lists `null` |
| `translatable: true` | `x-portable-translatable: true` (built into `portable:label` and `portable:text`) |
| `label:` | `title` |
| `FullyValidatable` | Not a keyword: decides whether `required` and non-null types are emitted |
| Type casting on save (`StorableConfigBase::castValue()`) | The normalization step, with a cast table defined in the spec |

### Required keys and `null`

Drupal enforces required keys and non-null values only for `FullyValidatable` types (`ValidKeysConstraintValidator`, `TypedConfigManager`). The converter does the same:

- **Types with `FullyValidatable`:** the root type or, below a dynamic type, the resolved type. There, `required` lists every key without `requiredKey: false`, and `null` is only allowed with `nullable: true`.
- **Other types:** no `required`, and scalar values also allow `null`. Example: core's `system.site.yml` has `mail_notification: null` without `nullable`.
- **Shared base types,** such as `config_entity`, follow the root type that uses them: a converter that emits them once emits them loosest, and the `FullyValidatable` type adds `required` and excludes `null` for the inherited keys.
- **`langcode`** is required in a `config_object` with translatable values (`LangcodeRequiredIfTranslatableValues`). Otherwise the rule above applies.

### Dynamic types

Config schema chooses a type by a data value, e.g. `settings: type: block.settings.[%parent.plugin]`. Portable Schema uses `portable-typeBy`, with a Relative JSON Pointer in `source`:

| Config schema expression | `source` pointer |
|---|---|
| `[%parent.plugin]` | `1/plugin` |
| `[%parent.%parent.x]` | `2/x` |
| `[%key]` | `0#` |
| `[id]` | `0/id` |

```json
"settings": {
  "$ref": "drupal:block_settings",
  "portable-typeBy": {
    "href": "drupal:block.settings.{plugin}",
    "source": { "plugin": "1/plugin" },
    "fallback": "drupal:block.settings.*"
  }
}
```

The base type (`block_settings`) is referenced next to `portable-typeBy`, so generic JSON Schema validators still check the common keys. Wildcard types such as `block.settings.*` become the `fallback`. A full example is in [`fixtures/examples/drupal`](../fixtures/examples/drupal).

### Config schema types

From `core/config/schema/core.data_types.schema.yml`:

| Config schema type | Portable Schema |
|---|---|
| `string`, `integer`, `float`, `boolean`, `email`, `uri`, `timestamp` | `portable:string`, `integer`, `number`, `boolean`, `email`, `uri`, `timestamp` |
| `label` | `portable:label` |
| `required_label` | `portable:label` + `minLength: 1` |
| `text` | `portable:text` |
| `uuid` | `portable:uuid` |
| `machine_name` | `portable:identifier` + `maxLength: 166` (the config entity ID limit) |
| `langcode` | `anyOf: [{"$ref": "portable:langcode"}, {"const": "site_default"}]` + `$ref` to the site's language catalog, which lists `site_default` too (core uses a `Choice` callback) |
| `color_hex` | `portable:color` |
| `weight` | `portable:weight` |
| `mapping`, `sequence` | `object`; `array` or keyed `object` |
| `undefined`, `ignore` | `{}` |
| `path`, `date_format`, `plural_label`, `bytes`, `config_dependencies`, `config_object`, `config_entity` | Drupal integration types, generated |

`email`, `uuid`, `machine_name` and `color_hex` also allow `""`, since their constraints skip it ([Empty strings](#empty-strings)).

## Typed Data

### Data types

| DataType | Portable Schema |
|---|---|

| `integer` | `portable:integer` (within ±(2^53 − 1), so JS agrees; Drupal goes up to ±2^63: a [known difference](#known-differences)) |

| `boolean` | `portable:boolean` |
| `binary` | `portable:binary` (base64) |

| `email` | `portable:email` |
| `uri` | `portable:uri`; for link fields see [Link fields](#link-fields) |
| `datetime_iso8601` | `portable:date-time`, or `portable:date` for date-only fields. Drupal stores datetimes as UTC without an offset (`Y-m-d\TH:i:s`); the integration adds `Z` on export and removes it on import |
| `duration_iso8601` | `portable:duration` |
| `timestamp` | `portable:timestamp` |
| `timespan` | `portable:timespan` |
| `enum` | `enum`, or `oneOf` + `const` + `title` |
| `any` | `{}` |
| `map` | `type: object` |
| `list` | `type: array` |
| `language_reference` | `portable:langcode` + the language catalog |
| `language`, `entity`, `entity_reference`, `field_item:*`, `filter_format`, `layout_section`, `resolvable_uri` | Drupal integration types, generated |

### Data definitions

| Typed Data | Portable Schema |
|---|---|
| `DataDefinition` | A schema; the DataType gives the type `$ref` |
| `MapDataDefinition`, `ComplexDataDefinitionBase` | `type: object` with `properties` |
| `ListDataDefinition` | `type: array` with `items` |
| Label, description | `title`, `description` |
| Required | `required` on the parent object |
| Constraints | See below |
| Runtime `TypedData` objects (`get()`, `getValue()`) | Out of scope: Portable Schema describes data, it doesn't wrap it |

## Constraints

| Constraint | Portable Schema |
|---|---|
| `Length` | `minLength`, `maxLength` |
| `Choice`, `AllowedValues`, `Enum` | `enum`, or `oneOf` + `const` + `title` for labeled options. `Choice` skips `null`: where `null` is allowed ([above](#required-keys-and-null)), the `enum` also lists `null` |
| `Regex` | `pattern`, converted from PCRE ([below](#regex-patterns)). Lookarounds, possessive quantifiers and PCRE-only syntax have to be rewritten |
| `Range` | `minimum`, `maximum` |
| `PositiveOrZero` | `minimum: 0` |
| `Count` | `minItems`, `maxItems` |
| `NotBlank` | Per JSON type: strings `minLength: 1`, arrays `minItems: 1`, objects `minProperties: 1`, booleans `const: true`, numbers nothing. `null` is excluded unless `allowNull`, also for `nullable` values. Not `required`: that is about the key, not the value |
| `NotNull` | A `type` without `null` |
| `Email`, `Uuid` | `portable:email`, `portable:uuid`; `""` allowed ([below](#empty-strings)). Drupal is stricter than the standard formats, so its exact check runs on the server: `drupal:Email`, `drupal:Uuid` |
| `LinkType`, `LinkExternalProtocols`, `LinkNotExistingInternal`, `LinkAccess` | `portable-check` (`drupal:LinkType`, …), run on the server ([Link fields](#link-fields)) |
| `ValidKeys` | `properties` + `unevaluatedProperties: false` |
| `ValidSequenceKeys` | `propertyNames` |
| `PluginExists`, `EntityBundleExists`, `ConfigExists`, `ExtensionExists` | `$ref` to a catalog: checkable live or statically against a site schema dump |
| `ValidReference`, `UniqueField`, `UniquePathAlias`, `ReferenceAccess` and other checks that need content or the current user | `portable-check`: run by a provider on the server; reported as unchecked where no provider is available |
| `Callback` | Case by case. Example: `block.block`'s region check becomes a catalog of the theme's regions, selected with `portable-typeBy` |

### Regex patterns

The converter turns `Regex` patterns into the ECMA-262 dialect of the [profile](../spec/profile.md#patterns), keeping PCRE's verdicts:

- **Delimiters** are stripped. `u` is implied; for `i`, see the [open questions](#open-questions).
- **A final `$`** becomes `\n?$`: core's patterns don't use `D`, so `$` also matches before a final newline. Example: `/^[a-z0-9_]+$/` becomes `^[a-z0-9_]+\n?$`.
- **`[^\PC…]` with `match: false`** becomes a positive pattern of explicit categories, without the unassigned `Cn`:
  - `label`: `^[^\p{Cc}\p{Cf}\p{Co}]*$`;
  - `text`: `^(?:[\x09\x0a\x0d]|[^\p{Cc}\p{Cf}\p{Co}])*$`;
  - `plural_label`: `^(?:\x03|[^\p{Cc}\p{Cf}\p{Co}])*$`.
  Unassigned code points stay a server check.
- **Other `match: false` patterns** become `not: {"pattern": …}`.
- **`""`:** `Regex` skips it, see [Empty strings](#empty-strings).

The generic types `portable:identifier` and `portable:color` don't get the `\n?$` rewrite.

### Empty strings

`Email`, `Uuid` and `Regex` skip `""`, and a link item with an empty `uri` is empty, so it is not validated. Where nothing else forbids it, the converter emits `anyOf: [{"const": ""}, {"$ref": "portable:email"}]`. The standard formats stay unchanged. Widgets and adapters look through this `anyOf` to the type.

### Link fields

- **The `uri` property** maps to `portable:uri` (RFC 3986). Drupal's `uri` DataType only needs a scheme, so it accepts values that are not URIs: a [known difference](#known-differences).
- **`route:` URIs:** core's `route:<nolink>`, `route:<none>` and `route:<button>` are not URIs. The integration percent-encodes `<` and `>` on export (`route:%3Cnolink%3E`) and decodes them on import.
- **Link semantics** (allowed protocols, `internal:` paths, existing routes, access) need the site: named checks `drupal:LinkType`, `drupal:LinkExternalProtocols`, `drupal:LinkNotExistingInternal` and `drupal:LinkAccess`, run on the server.

## Compatibility

Portable Schema must not be stricter than Drupal's validators, but it stays with the standard formats ([decision 0007](decisions/0007-pinned-checks-follow-the-standard.md)). Where Drupal is stricter, its exact check runs on the server as a named check. The verdicts behind this: [Drupal compatibility of formats and constraints](drupal-compatibility.md).

### Known differences

Values Drupal accepts and Portable Schema rejects:

| Value | Example | Why |
|---|---|---|
| UTF-8 email addresses (RFC 6531) | `jöe@example.com` | `email` is ASCII; `idn-email` is out of v1 |
| Non-URIs in `uri` | `https://example.com/ä`, `https://example.com/a b` | `uri` is RFC 3986 |
| Integers beyond ±(2^53 − 1) | `9007199254740993` | JS can't represent them; matters for `size: big` integer fields |
| JSON numbers for `decimal` values | `10` | `portable:decimal` is a string; the integration exports numbers as strings |
| `site_default` in `language_reference` | `site_default` | A Drupal keyword, not a language tag; only config `langcode` allows it |
| A trailing newline in `color_hex`, `machine_name`, `decimal` | `#ff0000\n` | Drupal's patterns don't use `D`; the generic types and formats don't carry that quirk |
| Custom language codes that aren't well-formed BCP 47 | `a-b` | Core's `VALID_LANGCODE_REGEX` is looser than RFC 5646 |

Numeric strings and booleans for `integer` and `float` are a normalization question (cast table), not a difference of the types.

Drupal is stricter, checked on the server:

- `email`: quoted local parts, address literals, single-label domains (`drupal:Email`);
- `uuid`: version and variant digits, the nil and max UUIDs (`drupal:Uuid`);
- link fields: see [Link fields](#link-fields);
- patterns: code points unassigned in Drupal's PCRE Unicode version.

### Open questions

- **Core issues,** upstream first:
  - `DecimalData`'s `#[JsonSchema]` emits `format: number`, which is not in the registry; `format: decimal` is;
  - `label` and the other `[^\PC]` patterns reject emoji ZWJ sequences and soft hyphens;
  - the `configurable_language` id pattern is not anchored, so it matches almost anything.
- **`iri` for link fields:** IRIs such as `https://example.com/ä` are realistic link input. Option: allow `iri` and `iri-reference` in v1, pinned as RFC 3987 syntax without IDNA processing, and map link fields to `iri`.
- **The `i` modifier:** `pattern` has no flags. Core uses `i` in `/^\//i` (path aliases), where it changes nothing; other uses need a rewrite.

## What the Drupal integration provides

- **Generated schemas** for config schema types, entity and field definitions, and plugin configuration.
- **Catalogs** of site facts: plugins per manager, bundles, fields, config entities, modules, themes, languages. Live, or in a site schema dump for one code base and module set.
- **Providers** for checks that need the running site (`portable-check`, `portable-refine`).
- **Value conversion** where Drupal stores values differently, e.g. UTC datetimes without an offset, decimals given as numbers, `route:` URIs with `<` and `>`.
- **Message translation** through `t()` (see [`architecture/messages.md`](architecture/messages.md)).

## Adoption: changing core

Draft plan. Core adopts Portable Schema through a few contracts, each with a default, so contrib code keeps working while it isn't portable yet.

### Contracts

**Definitions.** Data definitions provide their schema:

```php
public function getPortableSchema(PortableSchemaContextInterface $context): array;
```

- **The base implementation in `DataDefinition`** builds the schema generically:
  - `title` and `description` from label and description;
  - the type from the DataType (below);
  - constraints via their mapping;
  - `required` and `nullable`.
- **`ComplexDataDefinitionBase` and `MapDataDefinition`** add `properties` recursively; **`ListDataDefinition`** adds `items`.
- **Specific classes override it,** e.g. `EntityDataDefinition` (entity type and bundles as catalogs) or context definitions.
- **Field types need nothing extra:** field items are complex data built from their property definitions, so the same base implementation covers them.
- **The context** carries the registry (`$ref` or inline), the target (live or dump) and the language for labels.

**Companions.** Contracts beside the definition method, where the semantics live:

| Companion | Lives on | Contract | Default |
|---|---|---|---|
| DataType | DataType plugins | The attribute declares the portable type: `#[DataType(id: 'email', portable: 'portable:email')]`. Precedent: `#[JsonSchema]` on DataType classes since 11.2 | None: required. A DataType without a mapping is invalid |
| Constraint | Constraint plugins | `PortableConstraintInterface::getPortableSchema(array $options): array` | A custom check (`portable-check: {Name: options}`), run on the server |
| Catalog provider | Plugin managers, entity type manager | A catalog service per source: plugins per manager, bundles, config entities, modules, themes, languages | Generic from discovery; managers with special filtering override |

**Config schema YAML** needs no contract: the converter handles it, since its types are compositions of base types plus dynamic types.

### Fully portable

- **DataTypes always have a mapping.** The interface enforces it, and the set of primitive DataTypes in Typed Data is small; complex data is built from its property definitions.
- **Constraints don't all need a mapping.** A constraint without one is a **custom check**: validation logic in code, run on the server through `portable-check`. Custom validation code always has to be possible, so this is a regular case, not a gap.
- **A report** (like config_inspector's validatability report) lists the custom checks per schema, so it's visible what runs only on the server.
- **A core test fails** when a generic core constraint (`Length`, `Choice`, `Regex`, `Range`, …) is missing its mapping. That mirrors how the config validation initiative tracks `FullyValidatable`.

### Core patch

A core patch in two variants, so core can choose between enforcing the API and adding it compatibly. **We prototype variant A first.**

**Common to both:**
- the library as a core dependency;
- the `portable` property on the DataType attribute, declared by core DataTypes;
- mappings for core constraints;
- catalog providers and a site schema dump command;
- a `PortableSchema` constraint;
- a parity test that diffs Symfony validation and Portable Schema validation on core config;
- the core `json_schema` serialization format aligned with the same output.

| | Variant A: enforced API | Variant B: optional addition (BC) |
|---|---|---|
| Definitions | `getPortableSchema()` on `DataDefinitionInterface` | A new `PortableSchemaDefinitionInterface`, implemented by the core base classes |
| Constraints | `PortableConstraintInterface` optional: a constraint without it is a custom check | Same |
| Definition classes without the method | Not possible: every definition class implements it | Built generically from the definition interface |
| Consumers | Call the method | Check `instanceof`, otherwise use the generic build |
| BC | Breaks classes implementing the interfaces directly; fits a major release | Compatible; fits a minor release |
| Config validation | Runs through Portable Schema | Opt-in, e.g. per schema |

### Open questions

- **Which variant:** core's BC policy decides whether variant A is possible before a major release. Variant B can be followed by A, with a deprecation in between.
- **License:** the PHP implementation's dependencies must be compatible with GPL-2.0-or-later for core. opis/json-schema is Apache-2.0.
- **Runtime-dependent definitions** (hook alters, field config, enabled modules): schemas are generated per site and cached, so the cache invalidation needs care.
- **Two validators during the transition:** for mapped constraints, the Portable Schema result is authoritative; custom checks keep running on the server via `portable-check`.
- **Custom validation, not planned yet:** how custom checks are written, registered and, optionally, implemented in JS too, so they also run on the client. For later.
