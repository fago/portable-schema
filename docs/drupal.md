# Portable Schema and Drupal

How Portable Schema relates to what Drupal uses today to describe and validate data. Drupal's needs drive the design, but Portable Schema has no Drupal dependency; a Drupal integration generates the Drupal-specific types and catalogs.

## Overview

| Drupal | What it describes | Portable Schema equivalent |
|---|---|---|
| **Config schema** (`config/schema/*.schema.yml`) | Simple config and config entities | Schemas generated by the integration, using the type library |
| **Typed Data** (DataType plugins, data definitions) | Primitive and complex data, entity fields, plugin contexts | The type library; schemas generated from data definitions |
| **Validation constraints** (Symfony constraint plugins) | Rules on any typed data | Standard keywords, catalogs and `portable-check` |
| **SDC / Canvas props** (JSON Schema draft-04 / 07) | Component props | Portable Schemas are valid JSON Schema; down-level export for older drafts |

Config schema is built on Typed Data: each config schema type is a typed data definition, validated by the same constraint plugins.

## Config schema

### Structure

| Config schema | Portable Schema |
|---|---|
| `type: mapping` with `mapping:` keys | `type: object` with `properties` |
| `type: sequence` (list) | `type: array` with `items` |
| `type: sequence` (keyed) | `type: object` with `additionalProperties` |
| Type inheritance (`type: config_entity` plus extra keys) | `$ref` to the base type, plus the extra `properties` |
| Mappings closed by default (`ValidKeys: <infer>`) | Concrete types close with `unevaluatedProperties: false`; base types stay open |
| All keys required by default; `requiredKey: false` | `required` lists the required keys |
| `nullable: true` | `type: [<type>, "null"]` |
| `translatable: true` | `x-portable-translatable: true` (built into `portable:label` and `portable:text`) |
| `label:` | `title` |
| `FullyValidatable` | A schema-level flag, not a keyword |
| Type casting on save (`StorableConfigBase::castValue()`) | The normalization step, with a cast table defined in the spec |

### Dynamic types

Config schema chooses a type by a data value, e.g. `settings: type: block.settings.[%parent.plugin]`. Portable Schema uses `portable-typeBy`, with a Relative JSON Pointer in `source`:

| Config schema expression | `source` pointer |
|---|---|
| `[%parent.plugin]` | `1/plugin` |
| `[%parent.%parent.x]` | `2/x` |
| `[%key]` | `0#` |
| `[id]` | `0/id` |

```json
"settings": {
  "$ref": "drupal:block_settings",
  "portable-typeBy": {
    "href": "drupal:block.settings.{plugin}",
    "source": { "plugin": "1/plugin" },
    "fallback": "drupal:block.settings.*"
  }
}
```

The base type (`block_settings`) is referenced next to `portable-typeBy`, so generic JSON Schema validators still check the common keys. Wildcard types such as `block.settings.*` become the `fallback`. A full example is in [`fixtures/examples/drupal`](../fixtures/examples/drupal).

## Typed Data

### Data types

From `core/lib/Drupal/Core/TypedData/Plugin/DataType/`:

| DataType | Portable Schema |
|---|---|
| `string` | `portable:string` |
| `integer` | `portable:integer` (within ±(2^53 − 1), so JS agrees) |
| `float` | `portable:number` |
| `boolean` | `portable:boolean` |
| `binary` | `portable:binary` (base64) |
| `decimal` | `portable:decimal` (a string). Core's `#[JsonSchema]` on `DecimalData` emits `format: number`, which is not in the format registry |
| `email` | `portable:email` |
| `uri` | `portable:uri` |
| `datetime_iso8601` | `portable:date-time`, or `portable:date` for date-only fields. Drupal stores datetimes as UTC without an offset (`Y-m-d\TH:i:s`); the integration adds `Z` on export and removes it on import |
| `duration_iso8601` | `portable:duration` |
| `timestamp` | `portable:timestamp` |
| `timespan` | `portable:timespan` |
| `enum` | `enum`, or `oneOf` + `const` + `title` |
| `any` | `{}` |
| `map` | `type: object` |
| `list` | `type: array` |
| `language_reference` | `portable:langcode` + the language catalog |
| `language`, `entity`, `entity_reference`, `field_item:*`, `filter_format`, `layout_section`, `resolvable_uri` | Drupal integration types, generated |

### Data definitions

| Typed Data | Portable Schema |
|---|---|
| `DataDefinition` | A schema; the DataType gives the type `$ref` |
| `MapDataDefinition`, `ComplexDataDefinitionBase` | `type: object` with `properties` |
| `ListDataDefinition` | `type: array` with `items` |
| Label, description | `title`, `description` |
| Required | `required` on the parent object |
| Constraints | See below |
| Runtime `TypedData` objects (`get()`, `getValue()`) | Out of scope: Portable Schema describes data, it doesn't wrap it |

## Constraints

| Constraint | Portable Schema |
|---|---|
| `Length` | `minLength`, `maxLength` |
| `Choice`, `AllowedValues`, `Enum` | `enum`, or `oneOf` + `const` + `title` for labeled options |
| `Regex` | `pattern`, within the portable regex subset. Lookarounds, possessive quantifiers and PCRE-only syntax have to be rewritten |
| `Range` | `minimum`, `maximum` |
| `PositiveOrZero` | `minimum: 0` |
| `Count` | `minItems`, `maxItems` |
| `NotBlank` | `minLength: 1`, or `required` |
| `NotNull` | A `type` without `null` |
| `Email`, `Uuid` | `portable:email`, `portable:uuid` |
| `ValidKeys` | `properties` + `unevaluatedProperties: false` |
| `ValidSequenceKeys` | `propertyNames` |
| `PluginExists`, `EntityBundleExists`, `ConfigExists`, `ExtensionExists` | `$ref` to a catalog: checkable live or offline from a site schema dump |
| `ValidReference`, `UniqueField`, `UniquePathAlias`, `ReferenceAccess` and other checks that need content or the current user | `portable-check`: run by a provider on the server; reported as unchecked where no provider is available |
| `Callback` | Case by case. Example: `block.block`'s region check becomes a catalog of the theme's regions, selected with `portable-typeBy` |

## What the Drupal integration provides

- **Generated schemas** for config schema types, entity and field definitions, and plugin configuration.
- **Catalogs** of site facts: plugins per manager, bundles, fields, config entities, modules, themes, languages. Live, or in a site schema dump for one code base and module set.
- **Providers** for checks that need the running site (`portable-check`, `portable-refine`).
- **Value conversion** where Drupal stores values differently, e.g. UTC datetimes without an offset.
- **Message translation** through `t()` (see [`architecture/messages.md`](architecture/messages.md)).

## Adoption: changing core

Draft plan. Core adopts Portable Schema through a few contracts, each with a default, so contrib code keeps working while it isn't portable yet.

### Contracts

**Definitions.** Data definitions provide their schema:

```php
public function getPortableSchema(PortableSchemaContextInterface $context): array;
```

- **The base implementation in `DataDefinition`** builds the schema generically:
  - `title` and `description` from label and description;
  - the type from the DataType (below);
  - constraints via their mapping;
  - `required` and `nullable`.
- **`ComplexDataDefinitionBase` and `MapDataDefinition`** add `properties` recursively; **`ListDataDefinition`** adds `items`.
- **Specific classes override it,** e.g. `EntityDataDefinition` (entity type and bundles as catalogs) or context definitions.
- **`FieldItemDataDefinition` delegates to the field type** (below), since it is one generic class for all field types.
- **The context** carries the registry (`$ref` or inline), the target (live or dump) and the language for labels.

**Companions.** Contracts beside the definition method, where the semantics live:

| Companion | Lives on | Contract | Default |
|---|---|---|---|
| DataType | DataType plugins | The attribute declares the portable type: `#[DataType(id: 'email', portable: 'portable:email')]`. Precedent: `#[JsonSchema]` on DataType classes since 11.2 | Inherited from the parent class |
| Field type | Field item classes | `static portableSchema(FieldStorageDefinitionInterface $definition, PortableSchemaContextInterface $context): array`, beside `schema()` and `propertyDefinitions()` | Built from `propertyDefinitions()` in `FieldItemBase` |
| Constraint | Constraint plugins | `PortableConstraintInterface::getPortableSchema(array $options): array` | `portable-check: {Name: options}`: still checked on the server, not portably |
| Catalog provider | Plugin managers, entity type manager | A catalog service per source: plugins per manager, bundles, config entities, modules, themes, languages | Generic from discovery; managers with special filtering override |

**Config schema YAML** needs no contract: the converter handles it, since its types are compositions of base types plus dynamic types.

### Fully portable

- A schema is **fully portable** when every DataType and constraint in it has a mapping, so no `{}` fallback and no unintended `portable-check`.
- **A report** (like config_inspector's validatability report) shows what isn't portable yet.
- **A core test fails** when core config or core data types fall back. That mirrors how the config validation initiative tracks `FullyValidatable`.

### Phases

1. **Contrib** (`portable_schema` module, no core changes):
   - converter services per definition class, tagged and alterable, written so each moves 1:1 into the class's `getPortableSchema()` later;
   - mapping tables for DataTypes and constraints;
   - catalog providers, a site schema dump command;
   - a `PortableSchema` constraint;
   - a parity test that diffs Symfony validation and Portable Schema validation on core config.
2. **Core, minor release:**
   - the library becomes a core dependency;
   - **new interfaces**, implemented by the base classes: `PortableSchemaDefinitionInterface`, `PortableConstraintInterface`, plus the `portable` DataType attribute property and the static field type method;
   - core constraints and DataTypes declare their mappings;
   - catalog providers move into core;
   - the core `json_schema` serialization format aligns with the same output.
3. **Core, later minor releases:**
   - config validation runs through Portable Schema; Symfony validation keeps running for unmapped constraints;
   - classes that don't implement the new interfaces get deprecated.
4. **Core, next major:**
   - the new interfaces merge into `DataDefinitionInterface` and the constraint base;
   - config schema YAML becomes a legacy input format handled by the converter, or is generated from Portable Schemas.

### Open questions

- **BC policy:** a new interface plus deprecation is the usual route for adding methods. Whether core would accept adding the method to `DataDefinitionInterface` directly, given the base classes, is unverified.
- **License:** the PHP implementation's dependencies must be compatible with GPL-2.0-or-later for core. opis/json-schema is Apache-2.0.
- **Runtime-dependent definitions** (hook alters, field config, enabled modules): schemas are generated per site and cached, so the cache invalidation needs care.
- **Two validators during the transition:** for mapped constraints, the Portable Schema result is authoritative; unmapped ones keep running as `portable-check`.
