# Drupal example: block config

What a Drupal integration would generate for `block.block.*` config entities, converted from core config schema. For planning only; the real schemas are generated by the integration, not maintained here.

| File | Generated from |
|---|---|
| [`schemas/block.block.json`](schemas/block.block.json) | `block.block.*` in `core/modules/block/config/schema/block.schema.yml` |
| [`schemas/config_entity.json`](schemas/config_entity.json) | `config_entity` in `core.data_types.schema.yml`: open base type |
| [`schemas/block_settings.json`](schemas/block_settings.json) | `block_settings` in `core.data_types.schema.yml`: open base type |
| [`schemas/block.settings.fallback.json`](schemas/block.settings.fallback.json) | `block.settings.*`: fallback for plugins without their own schema |
| [`schemas/block.settings.system_branding_block.json`](schemas/block.settings.system_branding_block.json) | `block.settings.system_branding_block` in `system.schema.yml` |
| [`schemas/condition.plugin.json`](schemas/condition.plugin.json), [`schemas/condition.plugin.fallback.json`](schemas/condition.plugin.fallback.json) | `condition.plugin` and `condition.plugin.*` |
| [`catalogs/`](catalogs) | Site facts from one code base and module set: block plugins (`PluginExists`), modules, themes, Olivero's regions |
| [`block.block.cases.json`](block.block.cases.json) | Example config, valid and invalid, in the conformance format. All files in `schemas/`, `catalogs/` and the repo's `types/v1/` form the registry |

## What it shows

- **`settings: type: block.settings.[%parent.plugin]`** becomes:
  - a `$ref` to the open base `block_settings`;
  - `portable-typeBy` with `source: {"plugin": "1/plugin"}`;
  - `fallback` to `block.settings.*`.
- **`visibility`** does the same per condition, with `source: {"id": "0/id"}` (`[id]`).
- **`PluginExists`** and `ExtensionExists` become `$ref`s to catalogs. A site schema dump provides them.
- **`region`** depends on `theme`: `portable-typeBy` selects the theme's region catalog. Core uses a PHP callback for this.
- **Core's id pattern** uses a lookahead (`(?!\.)`), which is outside the portable regex subset. The converter rewrites it to an equivalent pattern.
- **Base types stay open; concrete types close the object.**
- **`required` is on the concrete type:** `block.block.*` is `FullyValidatable`, so it requires the base keys too. The base type `config_entity` has no `required`; it assumes a `FullyValidatable` user, so its keys don't allow `null`. The example leaves out the language catalog and `""` for `id` and `uuid`.

## Mapping

How Drupal's config schema types, Typed Data types and constraints map to Portable Schema is described in [`docs/drupal.md`](../../../docs/drupal.md).

## In a generic JSON Schema validator

Validating the cases with Ajv (2020-12, `strict: false`, with the files above as registry):

- The four cases that only need standard keywords give the expected result, catalogs included.
- The two cases that need `portable-typeBy` (an unknown key in plugin-specific settings, a region outside the theme) **pass**. Generic validators ignore `portable-typeBy`, so the result is more permissive, never wrong in the other direction.

`drupal:` IDs are placeholders for whatever ID scheme the integration uses.
