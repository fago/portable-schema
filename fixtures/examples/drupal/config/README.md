# Drupal showcase: config

What a Drupal integration would generate for two kinds of config entities, converted by hand from their config schema: core's `block.block.*` and Drupal Canvas' `canvas.component.*`. For planning only; the real schemas are generated by the integration, not maintained here.

Both runners run the cases. The registry of each case is the repo's `types/v1/` plus every file in [`schemas/`](schemas) and [`catalogs/`](catalogs).

### Mapping

- **`settings: type: block.settings.[%parent.plugin]`** becomes:
  - a `$ref` to the open base `block_settings`;
  - `portable-typeBy` with `source: {"plugin": "1/plugin"}`;
  - `fallback` to `block.settings.*`.
- **`visibility`** does the same per condition, with `source: {"id": "0/id"}` (`[id]`).
- **`PluginExists`** and `ExtensionExists` become `$ref`s to catalogs. A site schema dump provides them.
- **`region`** depends on `theme`: `portable-typeBy` selects the theme's region catalog. Core uses a PHP callback for this.
- **Core's id pattern** uses a lookahead (`(?!\.)`), which is outside the portable regex subset. The converter rewrites it to an equivalent pattern.
- **Base types stay open; concrete types close the object.**

### What the cases show

- A plugin with its own settings schema, and one that falls back to the base keys.
- An unknown plugin: one `enum` error listing the catalog's titles.
- An unknown key in plugin-specific settings: one `unknownProperty` error at `/settings`.
- A region outside the theme's region catalog, and an invalid value in the base type.

### In a generic JSON Schema validator

Validating the cases with Ajv (2020-12, `strict: false`, with the files above as registry):

- The four cases that only need standard keywords give the expected result, catalogs included.
- The two cases that need `portable-typeBy` (an unknown key in plugin-specific settings, a region outside the theme) **pass**. Generic validators ignore `portable-typeBy`, so here the result is more permissive. It can also be stricter: where `unevaluatedProperties: false` sits next to a `portable-typeBy`, the properties only the target declares count as unevaluated.

### Mapping

| Config schema | Portable Schema |
|---|---|
| `source`: `PluginExists` + `NotEqualTo: fallback` | `$ref` to the source plugin catalog + `not: {const: fallback}`, with Canvas' message as `x-portable-messages` |
| `source_local_id: type: canvas.component_source_local_id.[%parent.source]` | `portable-typeBy` on `1/source`; each target is its own catalog: SDC components, code components (`ConfigExists`), block plugins |
| `settings: type: canvas.component_source_settings.[%parent.%parent.%parent.source]` | `portable-typeBy` on `3/source` |
| `default_settings: type: block.settings.[%parent.%parent.%parent.%parent.source_local_id]` | `portable-typeBy` on `4/source_local_id`, with the block showcase's `block_settings` as base and `block.settings.*` as fallback. `{+source_local_id}` keeps derivative IDs like `system_menu_block:main` intact |
| `versioned_properties` items: `canvas.component.versioned.[%key].[%parent.%parent.active_version]` | A two-variable template on `0#` and `2/active_version` |
| Config schema's wildcard lookup: `versioned.active.<hash>` → `versioned.active.*` → `versioned.*.*` | `fallback` to `canvas.component.versioned.*`, which selects `versioned.{key}.*` with its own `portable-typeBy` and falls back to `versioned.*.*` |
| `type: canvas.component.versioned.*.*` inherited by `.active.*` | `$ref` to `versioned.*.*`; `.active.*` adds the typed `settings` |
| `SequenceKeysMatchRegex` on version keys | `propertyNames` with the pattern |
| `id`: `StringParts`; `active_version`: `Callback`; `prop_field_definitions`: `KeyForEverySdcProp`, `SequenceKeysMustMatch` | Named checks `drupal:<Constraint>` with the constraint's options |
| `PluginExists` for field types and widgets | `$ref`s to catalogs |

Left out: `ComponentStatusConstraint` and `ExtensionName`/`Callback` on `provider`, the per-prop constraints (`MatchesComponentPropRequiredness`, `NotNullIfRequiredComponentProp`, `ValidStructuredDataPropExpression`, `ValidSlotName`), the typed `field.storage_settings.*` / `field.value.*` and `derived_schema_metadata`'s keys. They follow the same patterns. The temporary `Choice` on `source` is left out too; the catalog takes its place.

### What the cases show

- **Valid:** an SDC component (Canvas' heading test fixture), a block component with typed `default_settings` and an old version whose settings are not validated, and a component whose active version is the special `fallback` version.
- **Named checks:** without callbacks, `drupal:Callback`, `drupal:StringParts` and `drupal:KeyForEverySdcProp` are reported as unchecked; a callback reports the ID mismatch.
- **Invalid:** the `fallback` source (with Canvas' own message), an unknown SDC component, an unknown key in the block's default settings, fallback metadata in the fallback version, an invalid version key, an unknown field widget.

### Gaps

- **Progressive wildcards.** Config schema replaces the last parts of a dynamic type name with `*` one at a time. `portable-typeBy` has a single `fallback`, so the second level needs a schema with its own `portable-typeBy`.
- **Constraint options that refer to data,** e.g. `KeyForEverySdcProp: "%parent.%parent.%parent.%parent.source_local_id"`. The named checks get a Relative JSON Pointer (`4/source_local_id`) as option; the spec doesn't define this yet.
- **Cross-field rules** such as `StringParts` stay named checks until `portable-compare` / `portable-refine` exist.
